# 文档治理

> Status: Accepted
> Owner: Documentation
> Last reviewed: 2026-10-23

## 原则

文档是产品与工程的一部分，不是交付后的补丁。文档应当帮助新开发者回答：

1. 项目要解决什么问题？
2. 当前哪些能力真实存在？
3. 某个模块的边界和事实来源是什么？
4. 新增模型、App 或协议需要修改哪些契约和测试？
5. 最近一次改动验证了什么，还缺什么？

## 文档分层

- `README.md`：项目入口和当前状态。
- `AGENTS.md`：人和 AI Agent 的工作规则。
- `docs/00-*` 与 `docs/01-*`：产品和范围。
- `docs/02-*` 至 `docs/06-*`：技术、执行、安全和测试。
- `docs/adr/`：重要且不易逆转的决策。
- `docs/guides/`：可重复执行的操作流程。
- `docs/HANDOFF.md`：当前进度、验证、风险和下一步。
- `docs/model-compatibility.md`：供应商能力与评测事实。

## 编写规则

- 明确区分“已实现”“计划中”“已放弃”。
- 使用可验证动词和命令，避免“优化了很多”“基本可用”等模糊表述。
- 跨文档链接使用相对路径。
- 代码片段必须与真实契约一致；计划中的 schema 标记 Draft。
- 重要决策记录替代方案、后果和迁移方式。
- 不把聊天记录、截图堆砌成规格；提炼成结论和验收条件。

## 文档状态

每份规格开头包含：

```text
> Status: Draft | Accepted | Superseded
> Owner: <role>
> Last reviewed: YYYY-MM-DD
```

- `Draft`：允许修改，尚不能作为稳定实现依据。
- `Accepted`：实现默认遵循，变化需要评审。
- `Superseded`：保留历史并链接替代文档。

## ADR 触发条件

以下变化必须新增 ADR：

- 平台、语言、框架或核心执行方式；
- 云端/本地职责边界；
- 模型供应商抽象、路由或协议版本；
- 权限模型、风险策略或数据保留；
- 存储、认证、部署或开源许可证；
- 会显著限制团队并行开发的决策。

ADR 编号连续，不覆写旧结论。新的决定通过新 ADR 取代旧 ADR。

## 每次变更的文档动作

1. 找到事实来源并检查现状。
2. 修改范围所对应的规格或 ADR。
3. 同步共享契约、测试和实现。
4. 更新兼容性、验收记录或操作指南。
5. 更新 `HANDOFF`。
6. 在 PR 模板中勾选文档和测试。

## HANDOFF 格式

```md
## Current State
## Completed
## Verified
## Open Risks
## Next Smallest Task
```

`Verified` 必须包含命令、设备、测试结果或明确未验证事项。`Next Smallest Task` 只保留一个可直接执行的任务。

## Agent 文档

- 根目录 `AGENTS.md` 定义全仓规则。
- 模块 `AGENTS.md` 只写该模块特有、必须靠近代码的规则。
- 不复制整份根规则，避免指令冲突和上下文超限。
- 每次调整架构边界或验证命令时，同步更新相应 `AGENTS.md`。
