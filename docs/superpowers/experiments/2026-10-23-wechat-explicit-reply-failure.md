# 微信当前会话显式回复实验失败记录

> 状态：暂停
> 日期：2026-10-23
> 设备：Redmi K60 / Android 15 / HyperOS OS3.0
> 微信：8.0.79
> 分支：`wip/wechat-explicit-reply-20261023`

## 结论

这条路线已经证明“手机 Agent 可以看微信、理解上下文并实际发出消息”，但还不能证明
“它每次都能安全地确认正确会话、正确草稿和正确发送结果”。

因此本分支不合并到 `main`，也不建议在开发者自己的日常微信或真实联系人上启用。

## 已经跑通的部分

- AccessibilityService 可以截取微信页面。
- 本机 ML Kit 可以从截图读取当前会话标题和最近消息。
- `ContextBuilder` 能把会话标题与近期消息交给 DeepSeek。
- DeepSeek 能根据近期消息生成最终回复，而不是复述“帮我回一下”。
- 剪贴板写入、长按输入框、OCR 定位“粘贴”并点击粘贴可以形成中文草稿。
- 把悬浮球移开后，可以点击微信发送按钮，并在聊天区看到真实发出的消息。
- 会话标题校验曾阻止任务进入错误会话；测试消息没有发到错误联系人。

## 失败原因

### 1. 微信不提供可用 UI 树

微信 8.0.79 对 `uiautomator` 和小猪搭手 AccessibilityService 都返回空树，因此标题、
输入框和消息只能依赖全屏截图 OCR。普通页面可直接读取控件语义，微信却只能依靠像素
和文字位置。

### 2. OCR 输出不稳定

真机中观察到的典型差异包括：

- “文件传输助手”被识别为“文件传輸助手”“文件伎輸助手”等。
- 独立的“粘贴”和“语音输入”按钮被合并成一行。
- 长消息被拆成多行，键盘联想词和按钮文字混入同一区域。
- 同一条消息在输入框、聊天区、联想栏中出现多个相似副本。
- 繁体/简体字符和少量错字会随截图时刻变化。

### 3. 固定坐标过脆

微信输入框、发送按钮、键盘和菜单的位置受键盘高度、滚动位置、字体和悬浮窗影响。
曾出现悬浮球覆盖发送按钮、点击发送却打开小猪搭手的情况；虽然通过移动悬浮球修复，
但说明单纯固定归一化坐标无法达到生产安全要求。

### 4. 发送后验证不可靠

真实消息已经出现，但 OCR 对消息方向和换行区域的识别并不稳定。曾出现：

- 消息已发送，状态机仍报告无法验证。
- 键盘建议词被当成草稿。
- 新消息和旧消息混在同一区域。
- ML Kit 连续识别偶发卡住，需要增加硬超时和异常兜底。

这些都可以继续修，但会和微信版本、输入法、屏幕缩放强绑定，维护成本过高。

### 5. 缺少可靠的幂等证据

微信没有提供消息 ID 或发送确认接口。应用只能从截图推断是否已发送，无法像系统
日历 Provider 那样回读稳定对象。因此“点击发送超时后再重试”有重复发送风险，而
“不重试”又可能漏发。

## 安全判断

发送消息是对外副作用，不能以“大概率正确”为发布标准。至少需要同时稳定确认：

1. 当前目标会话；
2. 输入框中的消息正文；
3. 发送后的新消息；
4. 失败时是否存在重复发送。

当前方案只能在不稳定 OCR 上近似满足前三项，第四项没有可靠证据，所以暂停。

## 保留价值

这次实验没有白做，它沉淀了：

- 截图读取与 OCR 的结构化接口；
- 当前会话上下文注入模型的链路；
- 长按菜单、剪贴板中文输入和发送按钮的实际校准；
- 悬浮窗遮挡控制按钮的真机问题；
- 驱动异常兜底、OCR 超时和界面区域校验；
- 微信版本变化时必须停止而不是盲目点击的安全原则。

## 重新启动条件

后续只有在满足至少一项时才建议重新评估微信技能：

- 微信或系统提供稳定的会话、消息和发送确认标识；
- 接入能输出控件结构或高置信度边界框的本机视觉模型；
- 建立专用测试账号、白名单会话和可回放的截图评测集；
- 能证明发送失败后不会重复发送；
- 只在用户明确说“帮我回”时执行，并默认关闭常驻自动回复。

在此之前，微信保持为可选实验技能，不阻塞通用 Android 能力和系统级技能。
